# Results guide

Start with [leaderboard.md](leaderboard.md) for scores or [interpretations.md](interpretations.md) for each model's own interpretation of every prompt. Open `interpretations.html` locally for prompt search, a model/provider selector, and vote details.

| Path | Contents | Generated by |
|---|---|---|
| `scores.json` | Scoring version, accepted crowd winners, prediction scores, confidence intervals, own-reading agreement, per-task consistency, baselines, costs, and providers | `node src/cli.ts report` |
| `leaderboard.md` | Human-readable summary of those aggregate metrics | `node src/cli.ts report` |
| `leaderboard.svg` | Prediction-accuracy bars with confidence intervals | `node src/cli.ts report` |
| `leaderboard-scatter.svg` | Score-versus-cost chart based on the README Results table | `node scripts/chart.mjs` |
| `leaderboard-scatter.png` | Raster version of the scatter chart embedded in the README | Exported from the SVG |
| `interpretations.md` | One row per prompt and one column per saved run, using only the second question | `node src/cli.ts interpretations` or `report` |
| `interpretations.html` | Searchable version of the own-interpretation table, including vote breakdowns | Same as above |
| `raw/<run>/predict/` | Saved responses to “Which reading did most people choose?” | A benchmark run |
| `raw/<run>/read/` | Saved responses to “Which reading is yours?” | A benchmark run |
| `*.log` | Console output from individual or batch runs; ignored by Git | Shell redirection during a run |
| `history/scoring-v1/` | Exact pre-v2 reports and charts, with provenance | Preserved snapshot |
| `.gitkeep` | Historical placeholder for an empty results directory | Not needed once outputs exist |

Each raw JSON file records one call: model, window/day, task, option order, request, raw answer, parsed quadrant and confidence, usage/cost, serving provider, errors, and timestamp. A filename such as `24-1.json` means window 24, option ordering 1. Use `data/windows.json` to look up the prompt for a window.

## Scoring v2

All current reports use scoring **v2**, independently of the generation prompt version (still v1) and npm package version. The [v1 snapshot](history/scoring-v1/) preserves the earlier numbers and charts. V2 was recalculated using the same saved responses; no model calls were repeated. npm package 0.1.5 predates this revision; the source commands below use v2.

A window's accepted crowd answers are every quadrant tied for its largest submission count, derived from the integer `counts`. The legacy singular `dominant` field is not authoritative for scoring. Republicans and Police Departments accept Performed × Dividing or Honest × Dividing; Freedom accepts Performed × Uniting or Honest × Dividing. Both prediction accuracy and own-reading agreement use this rule.

The baseline for a uniformly random final quadrant averages the number of accepted answers divided by four across windows: 25.5% here. The constant-class baseline counts a quadrant as correct whenever it is among the crowd co-winners; its value remains 31.5%. The lexical baseline is rescored against the same accepted sets and remains 33.9%.

Brier uses the model's reported confidence on its chosen quadrant, spreading the remaining probability equally over the other three. The target puts equal probability mass on each crowd co-winner. This is a co-winner calibration target, not the full human submission distribution. Missing or unresolved model answers are excluded from Brier but count as misses in attempted-window accuracy. Axis accuracy continues to use the separate crowd marginal majorities, omitting tied crowd axes. Crowd distance continues to compare the model's selected quadrant center with the crowd centroid.

## Consistency across option orders

A unique modal vote determines the model's final interpretation: 4–0, 3–1, and 2–1–1 are resolved; 2–2 and four-way ties are unresolved. Confidence never breaks a vote tie. Incomplete call sets retain their unique mode when one exists. An attempted window with no valid responses has no final answer and scores zero. Windows with no calls at all are not treated as attempted, so limited runs keep their smaller denominator.

For each task, `predict.consistency` and `read.consistency` report attempted windows, complete windows, 4/4 count and rate, invalid/missing call count, and the vote-pattern counts. The patterns are 4–0, 3–1, 2–1–1, 2–2, four-way tie, incomplete (one to three valid responses), and missing (zero valid responses). An incomplete 3/3 is not a 4/4 agreement. `instability` is a separate legacy metric for prediction vote ties or incomplete response sets; it does not mean every change across option orders.

These consistency measurements are descriptive. Repeating an identical option order under the same provider and generation settings is a separate control experiment needed to distinguish order effects from variation between identical calls.

## Own-interpretation aggregation

Only `read` responses are used in the interpretation tables. The scorer's unique modal vote across the four option orders determines the final interpretation, including a 2–1–1 plurality. A tie for the most votes is shown as **Tie**, not as a winning quadrant. **Missing** means there were no valid responses. An asterisk in Markdown or a dashed border in HTML marks fewer than four valid responses. Vote fractions count only valid responses. All crowd co-winning quadrants are shown for context; the table does not change prediction scores.

To regenerate just these tables without making model calls:

```bash
node src/cli.ts interpretations
```

`node src/cli.ts report` also regenerates them alongside the aggregate scores and leaderboard. These source commands require Node.js 22.18 or newer. The table command and scoring-v2 rules are part of this checkout and are not included in npm version 0.1.5.

## Suggested cleanup

Keep the raw responses as the source records, generated reports as the readable outputs, and logs in a separate `logs/` directory. Keep experiments outside the main comparison in the ignored `archive/` directory; only the eleven published runs belong in the active `raw/` directory.

For a reproducible public release, keep all eleven raw folders tracked in Git alongside the generated summaries and interpretation tables. Moving or renaming active raw directories should be coordinated with the runner and report paths. The obsolete `.gitkeep` placeholder can be removed separately; existing logs have been left in place.
